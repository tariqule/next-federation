Decide a response's cache header from a typed preload result, and observe each load, refusal and fallback as an event.

## Wait for a component to be ready

`Cart.preload(descriptor)` is unchanged. `Cart.preload(descriptor, { timeoutMs })` resolves a `PreloadResult` and never rejects. Every entry's `preloadRemoteComponent` takes the same options. It is not callable from an App Router Server Component, because the entry is a client module. Use `getServerSideProps` ([Pages Router](host-configuration.mdx#decide-the-cache-header-before-sending-html)) to decide a cache header before the HTML.

| `state`         | Meaning                                                                                                                | Renders                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `ready`         | The server loaded the module and its default export, not every browser file ([security](security.mdx#refused-builds)). | On the server.                         |
| `browser-only`  | Policy permits the browser (an unsigned build, `NF-028`) and the server will not render it (`NF-030`).                 | `fallback`, then the browser.          |
| `refused`       | Integrity or verification failed (`NF-027`, `NF-028` nested), or a shared module (`NF-036`).                           | `errorFallback`, also after hydration. |
| `failed`        | A transient server load failure (`NF-029`). The server retries after the cooldown.                                     | `fallback`, then the browser retries.  |
| `timeout`       | This caller stopped waiting. The shared load continues.                                                                | Your choice: omit, or `browserOnly`.   |
| `no-descriptor` | The descriptor was `null`.                                                                                             | `fallback`.                            |

`ms` is this caller's wait, and `code` accompanies `browser-only`, `refused` and `failed`. `timeoutMs` bounds only this caller. A `timeoutMs` above the runtime's load timeout yields `failed` (`NF-029`), and a later preload in the cooldown replays `failed`. In the browser, only `ready`, `refused` (`NF-036`), `failed`, `timeout` and `no-descriptor` arise.

`<Cart descriptor={d} browserOnly />` skips the server load: the server renders `fallback` and the browser loads. It never overrides a refusal, and the remote does not receive it. It is not a general fallback: use it for a `timeout` only when policy permits.

## Listen to component events

Event names and fields are unchanged: `component:load`, `component:error` and `component:descriptor`. Component events gain optional `phase` (`descriptor`, `load` or `render`) and `outcome`. `ms` is meaningful for the `load` and `descriptor` phases, and render-phase errors send `0`.

- **`component:fallback`** has a `reason` (`refused`, `browser-only`, `failed` or `render-error`). It fires only for a degraded render, never for the loading placeholder. An error and its fallback are two signals for one incident.
- **A caller timeout emits nothing.** A server `browser-only` fallback followed by a browser `component:load` is expected for an unsigned build.
- **Delivery:** the browser dispatches `nf:component` on `document`. The server calls the `onEvent` of the federation that resolved the descriptor, never by remote name, and nothing reaches the browser. Dev StrictMode can duplicate browser `refused` events.
- **Shared builds:** when two federations share a cached build, only the first gets the `load` event. Render events, including fallback, reach each.
- **Routing across processes** works when they create federations in the same order. Identical-config federations created in a different order can misroute.
- **Exhaustive handlers** without a `default` branch need a `component:fallback` case. The core `FederationEvent` also gains `component:load`.
